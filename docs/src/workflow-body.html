Ce que presque personne ne découvrePendant que les étiquettes sont affichées, tu peux taper une action au lieu d'une étiquette, puis désigner la cible :

C'est ce qui fait passer avy de « un saut » à « un opérateur qui agit à distance ». Ce sont ses réglages d'origine : rien à configurer, seulement à se rappeler une fois.

03Mises en situation

Six situations réelles, du premier geste au dernier.

Un bug remonte, tu n'as que le message d'erreur
Le réflexe coûteux est d'ouvrir le projet et de lire. Le bon réflexe est de laisser la machine localiser.
  1. Ctrl+B p → le projet se monte : agent, code, git, run.
  2. SPC / la chaîne exacte du message d'erreur. ripgrep sur tout le dépôt.
  3. Entrée sur le résultat, puis g d pour remonter aux définitions et C-o pour revenir. L'historique de sauts est ton fil d'Ariane.
  4. /fix dans opencode — le subagent debugger est en lecture seule et sa consigne est de reproduire avant de corriger.
  5. Le test qui échoue d'abord : /test. C'est ta propre règle, écrite dans ton AGENTS.md.
  6. SPC d b sur la ligne suspecte puis SPC d d si la lecture ne suffit pas. uv add --dev debugpy une fois par projet.
Explorer un dépôt que tu ne connais pas
Le piège est de lire des fichiers au hasard. Il faut une carte avant un texte.
  1. /scout dans opencode. C'est la seule commande marquée subtask: true : elle explore dans un contexte isolé et ne te rend que la carte. Trente fichiers lus, dix lignes rendues.
  2. SPC s i sur les fichiers qu'elle nomme — les symboles avant le code.
  3. C-c o n pour parcourir les définitions de haut niveau sans lire les corps.
  4. Ctrl+B f (file viewer) avec ] [ pour voir ce qui a bougé récemment : c'est là qu'est le code vivant.
  5. tokei pour le volume, serie pour la forme de l'historique.
Une idée à tester en trois minutes
Le coût réel n'est pas le code : c'est de décider où le mettre.
  1. Ctrl+B w puis Ctrl+N → ⚡ scratch. Un space jetable, un shell, un opencode, dans ~/scratch/<horodatage>. Aucun nom à choisir — c'est le point : une décision de nommage en moins, c'est un essai de plus.
  2. uv init && uv add pandas. Trois secondes.
  3. Si ça vaut quelque chose : git init, et le dossier devient un projet. Sinon tu le laisses mourir là.
Trois agents en parallèle
Le régime pour lequel herdr existe. Toute la difficulté est de ne pas regarder.
  1. Ctrl+B Shift+G trois fois — un worktree par tâche. Trois branches, trois répertoires, aucun conflit d'index possible.
  2. Brief les trois, puis pars. Un agent qui travaille est un agent qu'on ne regarde pas.
  3. Notification macOS → Ctrl+B o saute sur le pane qui t'attend.
  4. Ctrl+B d (reviewr) : lis le diff, v sélectionne, c commente, s renvoie tout à l'agent. Tu ne lis jamais le code dans le chat.
  5. Ctrl+B Alt+G lazygit, commit, retour. Le suivant t'attend déjà.
  6. Surveille Ctrl+B Alt+U : le contexte consommé par pane. Un agent à 90 % raconte n'importe quoi bien avant de le dire.
Ajouter une fonctionnalité à un projet existant
Là où la taille de tes commits se joue.
  1. Cadrer d'abord : Tab vers l'agent plan d'opencode, ou /explain. Un modèle de raisonnement sur la conception, un modèle de code sur l'exécution.
  2. Écrire. SPC w V pour ouvrir le test à côté du code — la majuscule, qui splitte et y va.
  3. Committer en cours de route, pas à la fin. C'est le point qui change tes chiffres : médiane 72 lignes, p90 1 613.
  4. Un oubli sur un commit déjà fait ? git absorb — il est installé chez toi et range la correction dans le bon commit tout seul.
  5. /review avant de pousser. Le subagent reviewer est en lecture seule et ne remonte que les vrais défauts.
Relire et livrer
  1. Ctrl+B d reviewr, portée b (toute la branche) pour voir ce que tu livres vraiment, pas seulement le dernier tour.
  2. make test — ou Ctrl+B Alt+A → « Tests », qui détecte le runner tout seul.
  3. /commit puis /pr. Le git push demandera confirmation : c'est voulu, c'est dans tes règles de permission.
  4. repos-status de temps en temps : ce qui traîne, en une seconde, sur les 28 dépôts.
